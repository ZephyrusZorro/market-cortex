# Phase 2 deterministic analytics and market state

Phase 2 reads Phase 1 `PostgresCatalog.bars` and never edits an observation, Parquet artifact, or dataset manifest. A request fixes the instrument, provider when needed, raw/adjusted basis, daily interval, inclusive session-date window, `as_of` availability cutoff, feature name/version, parameters, and a resolved source manifest. The output records observation and source-batch IDs, calendar identity/version, venue, currency, code hash, units, null reasons, coverage, freshness, calculation time, and elapsed time. `feature_id` and `snapshot_id` hash deterministic inputs and values; wall-clock calculation time is deliberately excluded from those IDs.

The feature registry in `src/market_cortex/features.py` exposes 38 named definitions, default parameters, required fields, units, supported interval, minimum-history rule and count, feature version `1.0.0`, and calculation version `daily_float64_v1`. The actual source hash of the feature engine plus numerical kernels travels with each result. [Version locks](VERSION_LOCKS_2026-10-03.json) and a test detect same-version code drift. A semantic change requires a new calculation version and preserved older code. The Phase 2 Git release commit identifies the code snapshot needed to reproduce a result. No arbitrary function name or Python expression from a request is executed.

## Input and null policy

- Input is a Phase 1 visible daily bar, pinned to the requested manifest and selected at one explicit `as_of`. The source provider must be unambiguous. Multiple visible providers require an explicit `provider_id`; duplicate visible dates fail closed.
- Expected sessions come from the venue calendar. Missing expected sessions remain null in the analytical array and break rolling windows. A calculation does not compress a window across a missing bar. For a 24/7 crypto venue, expected sessions are consecutive UTC dates. Equity calendars require imported, versioned exchange sessions before use.
- Sessions before `instrument.valid_from` or after `valid_to` are marked `INSTRUMENT_NOT_VALID`, excluded from eligible-session coverage, and cannot seed later indicators. The response distinguishes calendar-expected sessions from instrument-eligible sessions.
- Quarantined and unknown-availability Phase 1 rows are excluded by the Phase 1 reader. A missing Phase 2 point is marked `NO_VISIBLE_VALID_BAR`; this alone cannot distinguish never fetched from quarantined. `INPUT_UNAVAILABLE` identifies missing fields such as volume. `INSUFFICIENT_HISTORY_OR_GAP` identifies warm-up or broken windows. No unavailable value is replaced by zero.
- The requested `as_of` applies to every point in one feature result. Earlier research decisions require their own earlier `as_of` requests; a present-day as-of applied to old sessions is a retrospective view, not a pointwise historical decision simulation. Backfilled Binance bars first observed locally on 2026-10-03 are unavailable to a replay cutoff before that arrival.
- Numerical kernels use float64 after Phase 1 decimal validation. Non-finite results serialize as null. This is deterministic for the same code/runtime and input set, with tolerance based tests for floating point results. Exact monetary accounting remains outside this feature layer.

## Calculation conventions

The rules below are the canonical `daily_float64_v1` choices. TA-Lib's [official indicator catalog](https://ta-lib.github.io/ta-lib-python/func_groups/momentum_indicators.html), [overlap studies](https://ta-lib.github.io/ta-lib-python/func_groups/overlap_studies.html), and [volatility studies](https://ta-lib.github.io/ta-lib-python/func_groups/volatility_indicators.html) show the common indicator families, but libraries can differ in seeding and warm-up. The project fixes those choices below. NumPy documents [population versus sample standard deviation](https://numpy.org/doc/stable/reference/generated/numpy.std.html) through `ddof`.

| Family | Implemented features | Exact convention |
| --- | --- | --- |
| Returns | `arithmetic_return`, `log_return`, `cumulative_return`, `rolling_return`, `roc`, `gap_return` | Adjacent close ratio minus one; natural log of adjacent close ratio; first visible uninterrupted close is cumulative baseline; rolling return compares closes `period` completed session steps apart and requires all intervening sessions; ROC is rolling return ×100; gap uses current open versus prior close. Positive prices are required for ratios and logs. |
| Averages | `sma`, `ema` | SMA is the arithmetic mean of a full close window. EMA uses α=2/(period+1), seeded at the first complete SMA; a missing session resets its seed. Configurable integer periods 1–1000 where mathematically valid. |
| Trend | `price_vs_ma`, `ma_slope`, `ma_alignment`, `higher_high_lower_low`, `trend_persistence`, `trend_strength` | Price versus SMA and SMA slope are percentage differences; alignment is sign(fast SMA−slow SMA), requiring fast<slow; structure compares maxima and minima of adjacent nonoverlapping `period`-session blocks; persistence is positive-return share minus negative-return share; strength is (fast SMA−slow SMA)/ATR14, null if ATR is zero. |
| Momentum | `rsi`, `macd`, `macd_signal`, `macd_histogram` | RSI seeds mean gains/losses from `period` consecutive close changes, then uses Wilder `(previous×(period−1)+new)/period`. Flat gains/losses yield 50; no losses with positive gains yields 100. MACD=EMA(fast)−EMA(slow), signal=EMA(signal period) of MACD, histogram=line−signal. Defaults 12/26/9. |
| Volatility | `rolling_std`, `annualized_volatility`, `true_range`, `atr`, four `bollinger_*`, `rolling_high_low_range`, `volatility_percentile` | Rolling std is sample (`ddof=1`) std of arithmetic returns. Annualized volatility is sample std of log returns ×√365 for 24/7 markets or ×√252 for regular sessions unless explicitly overridden. First true range is high−low; later TR is max(high−low, |high−prior close|, |low−prior close|). ATR uses Wilder smoothing seeded by a full TR SMA. Bollinger middle is close SMA; upper/lower use `deviations` × population (`ddof=0`) close std; bandwidth=(upper−lower)/middle×100. High-low range divides the period maximum high minus minimum low by minimum low. Volatility percentile uses the midrank empirical percentile of the current annualized-volatility value within `rank_window` values: `(count below + 0.5×count equal)/N×100`, so a flat rank window yields 50. |
| Volume | `average_volume`, `relative_volume`, `volume_change`, `volume_zscore`, `price_volume_confirmation` | Source volume is never inferred. Relative volume=current/rolling mean; change=current/prior−1; z-score uses sample std and is null for zero variance; confirmation is sign(daily close return)×relative volume. Binance base-asset traded volume is a **volume proxy**, not order-book liquidity. |
| Drawdown | `running_peak`, `drawdown`, `maximum_drawdown`, `drawdown_duration`, `recovery_state` | Running peak is the highest close in the uninterrupted request window; drawdown=close/peak−1, maximum is the running minimum drawdown, duration counts sessions since the latest equal/new close peak, recovery state is 1 at an equal/new peak and 0 otherwise. Missing sessions reset these paths. |

Parameter validation rejects unknown keys, invalid ranges, `fast>=slow`, non-integer periods, and nonpositive Bollinger deviations. Warm-up values remain null. The registry reports the required observation count after parameter resolution. The default 200-session SMA needs 200 complete sessions; RSI14 needs 15 closes; MACD(12,26,9) histogram needs 34 closes. Numerical tests use hand-calculated small series, seeded invariant tests, and tolerance comparisons.

## Cross-series alignment, breadth, and comparison

`same_session` aligns identical venue/calendar/version and session date, and requires equal quote currency or an explicit FX conversion with rate source, availability and manifest lineage. It does not silently align an NSE date with a Binance UTC date. `completed_at_utc_cutoff` instead uses the target bar's UTC end plus a stated lag as a decision cutoff. A reference bar must have ended, become available, and remain within a stated maximum age at that cutoff. An optional FX rate must be positive, sourced and known by the request `as_of`; missing rates produce null comparisons. These policies preserve the actual paired observation IDs and reference session dates.

Relative strength is `(target_t/target_t−p)/(reference_t/reference_t−p)−1`, requiring `p+1` paired closes. Rolling correlation is Pearson correlation of `p` aligned **log-return pairs**, requiring `p+1` paired positive closes. Each point reports the method, window, actual return-pair count, coverage, missingness, and, when consecutive windows are available, absolute change from the previous rolling correlation as a simple stability diagnostic. Zero-variance correlation is null. FX-converted results carry a separate FX manifest ID.

Breadth names its exact universe and denominator. `binance_pilot_5` means BTCUSDT, ETHUSDT, SOLUSDT, BNBUSDT, and XRPUSDT only. `above_sma`, positive lookback return, new N-session high, new N-session low, advancing, declining, and unchanged use eligible members per metric. New highs/lows compare today's extrema with the **prior** period extrema. Missing or insufficient members are excluded from each metric's denominator and listed, while total universe size remains visible. Mixed-calendar breadth is rejected until an explicit comparable evaluation policy exists.

## Market-state vector and regime rules

`MarketStateSnapshot` computes on demand for a named, manifest-pinned universe. Each dimension records its category, metrics, feature/comparison/breadth evidence IDs, scope, daily timeframe, manifest, rule version and code hash, eligible and total member counts, freshness, and an unknown reason. The initial dimensions are BTC trend, BTC momentum, BTC volatility, BTC traded-volume proxy, five-member participation, five-member breadth, four-alt relative strength versus BTC, four-alt correlation versus BTC, a constrained risk-appetite proxy, freshness, and uncertainty. Five members do **not** measure global crypto breadth or global risk appetite.

- BTC trend is `up` when close>EMA20>SMA50 and SMA20 slope over five sessions is positive; `down` uses reversed inequalities and negative slope; otherwise `mixed` or `unknown`.
- BTC momentum is `positive` for RSI14>55 and positive MACD histogram, `negative` for RSI14<45 and negative histogram; otherwise `mixed` or `unknown`.
- BTC volatility percentile over 90 realized-volatility values is `elevated` at ≥80, `subdued` at ≤20, otherwise `middle`; unavailable rank is `unknown`. BTC relative volume20 is `elevated` at ≥1.2, `thin` at ≤0.8, otherwise `typical` or `unknown`.
- Breadth is `broad_positive` when both above-SMA20 and positive-return20 percentages are ≥80, `broad_negative` when both are ≤20, otherwise `mixed`; each requires at least max(3, universe size−1) eligible members.
- Alt relative strength requires at least three valid alt/BTC pairs. Mean positive ratio is `alts_outperforming`, otherwise `btc_outperforming`. Correlation requires at least three valid pairs and is `high` at mean Pearson ≥0.75, `low` below 0.3, otherwise `middle`. The risk-appetite proxy combines alt strength with five-member positive-return breadth; it can remain `mixed` despite broad positive breadth.
- The regime rule set returns `insufficient_data` if required trend/momentum/volatility is unknown, participation is incomplete, or freshness is stale. Otherwise matching uptrend/positive momentum or downtrend/negative momentum yields directional regimes split by elevated versus other volatility; disagreement yields `mixed`. Fired rule IDs and evidence are included. There is no opaque composite score.

## API, CLI, storage, and operations

Read-only routes: `GET /api/v1/features`, `/api/v1/features/series`, `/api/v1/features/compute`, `/api/v1/comparisons`, `/api/v1/market-state`, and `/api/v1/regime`. Feature routes take `name`, `instrument_id`, `from`, `to`, optional `as_of`, `manifest_id`, `provider_id`, `adjustment_basis`, and approved numeric parameters. Comparisons require target/reference IDs and a policy/window. Market-state routes require `history_from` and `evaluation_date`; they currently expose the exact Binance pilot universe. Existing loopback-only middleware and no-write policy apply.

CLI commands `compute-feature` and `compute-market-state` use the same service; `compute-feature --series` includes every point. Example after setting local `MARKET_CORTEX_DATABASE_URL` and `MARKET_CORTEX_DATA_ROOT`:

```powershell
.\.venv\Scripts\python.exe scripts\market_cortex.py compute-feature --name rsi --instrument-id 'PASTE-LOCAL-UUID' --from 2025-09-01 --to 2026-10-01 --provider-id binance --parameters '{"period":14}'
.\.venv\Scripts\python.exe scripts\market_cortex.py compute-market-state --history-from 2025-09-01 --evaluation-date 2026-10-01 --manifest-id 'PASTE-PINNED-MANIFEST'
```

Derived analytics are currently computed on demand; no duplicate feature tables or Redis cache were added. A later cache key must include feature/calculation/code versions, parameters, instrument, provider, interval, adjustment basis, manifest, as-of and observation window. Observability is returned as metadata (manifest, source count, warm-up/null reason, version/hash, elapsed milliseconds) without logging secrets. The [Phase 2 exit report](../planning/PHASE_2_EXIT_MATRIX_2026-10-03.md) records live pilot validation and limits.
