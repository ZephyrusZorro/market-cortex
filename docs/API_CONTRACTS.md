# API Contracts (Phase 1 and 2 read slices)

**Baseline:** [Phase 0 §5](architecture/PHASE_0_BASELINE_2026-09-26.md). [Registry](../packages/contracts/registry.schema.json).

Implemented read routes: `GET /api/v1/health`; `GET /api/v1/instruments?query=...&as_of=...` (mapping candidates and explicit ambiguity); `GET /api/v1/calendars/{venue_id}/sessions?from=...&to=...`; `GET /api/v1/bars?instrument_id=...&interval=P1D&from=...&to=...&as_of=...&manifest_id=...&adjustment_basis=raw&provider_id=...&offset=...&limit=...`; `GET /api/v1/coverage?instrument_id=...&from=YYYY-MM-DD&to=YYYY-MM-DD&as_of=...&manifest_id=...`; `GET /api/v1/data-health`; `GET /api/v1/manifests/{id}`. The CLI binds to loopback and middleware rejects non-loopback clients. No write or order routes exist. Bars include complete observation envelopes and retain conflicting providers; no silent average. `as_of` is a UTC availability cutoff, and `manifest_id` pins a published dataset. Coverage gaps use `NO_VISIBLE_OBSERVATION_AT_CUTOFF`: a missing visible bar may never have been ingested or may be excluded by availability or quality rules. The API does not interpolate OHLC. The current API uses offset pagination and a simplified error shape; cursor stability and complete error/coverage taxonomy are not finished. OpenAPI is generated at `/docs`.

Internal `DomainEvent` envelope: `event_id`, `event_type`, `schema_version`, `occurred_at`, `recorded_at`, `aggregate_id`, `correlation_id`, `idempotency_key`, `payload_ref`. `occurred_at` is domain event time; `recorded_at` is commit time. Outbox commits atomically with transactional records and references a committed data manifest; subscribers tolerate duplicates, retries and reordered delivery. Event types are namespaced and versioned; no event contains unconstrained provider payload or owner secrets. A new feed kind adds a payload schema without changing the envelope.

## Phase 2 deterministic analytics

Read-only routes: `GET /api/v1/features` lists the versioned registry; `GET /api/v1/features/series` returns every expected-session point; `GET /api/v1/features/compute` returns the latest point plus the calculation's lineage and quality summary; `GET /api/v1/comparisons` returns rolling relative strength or Pearson correlation with explicit alignment, window, count, coverage, missingness and stability; `GET /api/v1/market-state` returns the vector snapshot for the exact Binance pilot universe; and `GET /api/v1/regime` returns its transparent rule result. The existing loopback-only middleware applies. No analytics POST or broker/order route exists.

Feature routes require `name`, `instrument_id`, inclusive session dates `from`/`to`; accept `as_of`, `manifest_id`, `provider_id`, `adjustment_basis`, and approved numeric parameters (`period`, `fast`, `slow`, `signal`, `slope_period`, `rank_window`, `annualization`, `deviations`). The full result reports resolved manifest, availability cutoff, provider, venue/calendar, adjustment basis, feature/calculation version and code hash, source observation/batch lineage, units, warm-up, missing dates, freshness, elapsed time and null reasons. The scalar route reports observation count and the latest input observation ID; the series route carries all per-point evidence. An ambiguous multi-provider series is rejected until a provider is selected.

Comparison routes take target/reference instrument IDs, an inclusive date window, `kind=relative_strength|correlation`, `window`, provider selectors, and `alignment_policy=same_session|completed_at_utc_cutoff`. The latter exposes maximum reference age and decision cutoff lag in hours. Mixed currencies require a sourced FX series through the internal alignment contract; the HTTP comparison route currently fails closed for mixed currencies because no verified FX feed is configured.

Market-state routes take `history_from`, `evaluation_date`, optional `as_of`, and `manifest_id`. They currently resolve the five named Binance pilot mappings known at `as_of`. The result includes ten evidence-backed dimensions plus an uncertainty dimension, each with category, metrics, evidence references, coverage, freshness and unknown reason, along with the scoped breadth snapshot and regime rules. See [calculation semantics](analytics/PHASE_2_ANALYTICS.md).
